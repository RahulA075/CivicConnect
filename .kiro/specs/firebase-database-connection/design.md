# Design Document — Phase 14: Firebase + Database Connection

## Overview

Phase 14 wires real Firebase credentials into the already-built skeleton so that
the full push-notification pipeline is live: Flutter app ↔ Firebase Cloud
Messaging ↔ Spring Boot backend ↔ PostgreSQL.

No new runtime architecture is introduced. Every class, table, and endpoint
already exists. This phase is about:

1. Injecting real credentials (replacing stubs and placeholders).
2. Adding the missing `deactivateStaleToken` behaviour to
   `NotificationServiceImpl` (surfaced by Req 9).
3. Writing the two integration tests (Req 7 & 8).
4. Producing the `FIREBASE_SETUP.md` documentation (Req 10).
5. Verifying the build and static-analysis toolchains pass.

---

## Architecture

### Data Flow (unchanged from prior phases)

```
Flutter App
  │  (1) Firebase.initializeApp(DefaultFirebaseOptions.currentPlatform)
  │  (2) FirebaseMessaging.getToken()
  │  (3) POST /api/v1/notifications/device-token  {token, platform}
  ▼
Spring Boot Backend
  │  (4) NotificationController.registerToken()
  │  (5) NotificationServiceImpl.registerToken()
  │       ├─ deactivate old row in device_tokens (upsert)
  │       ├─ INSERT new device_tokens row
  │       └─ FcmPushService.subscribeToTopic() [NEARBY, ANNOUNCEMENT, EMERGENCY*]
  ▼
PostgreSQL  ──  device_tokens table

Later, when an issue status changes:
  NotificationServiceImpl.send()
  └─ FcmPushService.sendToToken() / sendMulticast()
     └─ Firebase Admin SDK → FCM → device
```

### Credential Resolution (FirebaseConfig — existing)

```
Startup
  ├─ app.notification.fcm-credentials-path set?
  │    └─ YES → FileInputStream(path)
  ├─ classpath:firebase-service-account.json exists?
  │    └─ YES → ClassPathResource
  └─ Application Default Credentials (GCP / Cloud Run)
       └─ unavailable → log WARN, push disabled (graceful no-op)
```

**Current state:** All values are `STUB_*` placeholders with zero App IDs.

**Required state:** Real values generated by `flutterfire configure --project=civicconnect-dev`.

| Field | Platform | Source |
|---|---|---|
| `apiKey` | android / ios / web | Firebase Console → Project Settings → General → Your apps |
| `appId` | android / ios / web | Firebase Console → app-specific |
| `messagingSenderId` | all | Firebase Console → Project Settings → Cloud Messaging → Sender ID |
| `projectId` | all | `civicconnect-dev` |
| `storageBucket` | all | `civicconnect-dev.appspot.com` |
| `iosBundleId` | ios only | `com.civicconnect.app` |

**Recommended update method:** `flutterfire configure` (auto-generates the file).
Manual editing is acceptable but error-prone.

### 5. `NotificationServiceImpl` — stale token deactivation (new behaviour)

**Gap identified in Req 9:** `FcmPushService.handleFcmError()` logs the stale
token warning but does not call back into `NotificationServiceImpl` to set
`is_active = FALSE`. The coupling needs to be added.

**Design decision — callback via interface:**

```
FcmPushService
  sendToToken(token, …)
    catch FirebaseMessagingException
      if UNREGISTERED | INVALID_ARGUMENT
        staleTokenCallback.accept(token)   ← new @Setter injected by NotificationServiceImpl

NotificationServiceImpl
  @PostConstruct
  void wireStaleTokenCallback() {
      fcmPushService.setStaleTokenCallback(this::deactivateStaleToken);
  }

  public void deactivateStaleToken(String token) {
      deviceTokenRepository.deactivateByToken(token);
  }
```

For `sendMulticast`, the existing `BatchResponse` loop is extended in
`NotificationServiceImpl.sendPushToUser()` — after calling
`fcmPushService.sendMulticast(tokens, …)` the method needs to also call the
deactivation for each failed token. This requires `sendMulticast` to return
per-token failure information.

**Revised `sendMulticast` signature:**

```java
// Returns list of tokens that failed with UNREGISTERED / INVALID_ARGUMENT
public List<String> sendMulticastWithStaleReturned(
        List<String> tokens, String title, String body, Map<String, String> data)
```

Alternatively (simpler), inject a `Consumer<String>` stale-token callback into
`FcmPushService` the same way as `sendToToken`, so that `sendMulticast` also
invokes the callback per-failure inside `FcmPushService` itself. This is the
chosen approach — it keeps the stale-deactivation logic in one place.

### 7. Integration Tests

#### `FcmTokenRegistrationTest` (Req 7)

- `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `@Tag("integration")`
- Testcontainers PostgreSQL (already in `build.gradle.kts`)
- `FcmPushService` replaced with a Mockito mock `@MockBean`
- JWT test helper creates an authenticated user and issues a token
- Tests:
  - `POST /device-token` → 200, row in DB with `is_active = TRUE`
  - Second `POST` same token → old row `is_active = FALSE`, new row `is_active = TRUE`, count = 1
  - `DELETE /device-token` → 200, row `is_active = FALSE`

#### `FcmPushDispatchTest` (Req 8)

- `@SpringBootTest` (no web layer needed — tests service directly) + `@Tag("integration")`
- Testcontainers PostgreSQL
- `FcmPushService` mocked with `@MockBean`
- Tests:
  - 1 active token → `sendToToken()` called once with correct args
  - 2 active tokens → `sendMulticast()` called once with both tokens
  - `push_enabled = FALSE` in preferences → neither FCM method called
  - `Notification` row persisted in DB
